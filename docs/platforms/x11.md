# X11

`crates/x11` uses `x11rb`, which is pure Rust, with no libxcb. It targets EWMH window managers and is tested with Xfwm4, with and without its compositor. What it shares with the other Linux adapters is in [Linux](linux.md).

## Threads

`src/app.rs`. X has no main-thread rule. The event loop reads X events on one connection, and the engine thread makes window requests on a second. Key grabs and input selections go out on the event connection, so their events arrive where they're read.

The overlay has a thread of its own, which also drives the tray.

## Finding and moving windows

`src/windows/`.

- **Managed windows** come from `_NET_CLIENT_LIST_STACKING`, top first. The window under the pointer is the topmost visible one containing it.
- **Frames** include the window manager's decorations (`_NET_FRAME_EXTENTS`) and leave out client-side shadows (`_GTK_FRAME_EXTENTS`).
- **Writes** are `_NET_MOVERESIZE_WINDOW` requests, after taking a maximized window out of its maximized state.
- **Focusing** sends `_NET_ACTIVE_WINDOW`, as a pager would.
- **App identifiers** come from `WM_CLASS`.
- **Eligibility.** A window is eligible when it isn't full screen, is a top-level window of normal type that isn't transient, and allows moving and resizing.

## Observing

`src/events.rs`. Moves come from `ConfigureNotify` on the windows Snappy tracks, not on the root window, which would wake Snappy for every frame of every window.

Root window properties report windows opening and closing, focus, and desktop changes. RandR, `_NET_WORKAREA`, and `Xft.dpi` report display changes, and work areas are worked out per monitor from panel struts.

## Input

`src/input.rs`. XInput 2 raw button and motion events on the root window arrive even while the window manager grabs the pointer for a move, and grab nothing themselves.

Raw key events are selected only while drag monitoring is on. They follow the modifier keys in event order from the keys down when it started, so a release reports the modifiers held when the button came up. Asking the server afterwards could already see a modifier let go right behind the button.

## Shortcuts

`src/hotkeys.rs`, `src/keymap.rs`. Shortcuts are `XGrabKey` on the root window, once for each combination of Caps Lock and Num Lock. A refused grab means another client holds the chord, which doubles as the availability probe.

On evdev keymaps, physical key codes map straight to keycodes, so shortcuts stay on the same keys on every layout. Detectable auto-repeat makes a held shortcut fire once.

## Overlay

`src/overlay/`. Each display gets two override-redirect windows, one for zones and one for window outlines, with an ARGB visual and an empty input region, so they take no clicks.

- Without a compositing manager, the Shape extension cuts each down to the zone borders and the boxes behind numbers and captions.
- X11 has no accent color to read, so zones use the default blue.
- The outlines window is raised again whenever the active window changes, since window managers raise the window they focus.

## Caps Lock as the Snappy key

`src/caps_lock/`. Snappy rewrites the Caps Lock key's XKB definition for the session: no symbol, an action that sets the Snappy key's modifiers while held, and no repeat. Snappy's grabs and every other client see the modifiers themselves, and Caps Lock never locks.

- **Presses.** A passive grab on the key reports its press. Only while it's down are raw key and button presses selected, to notice that something else was used.
- **A tap** toggles Caps Lock through XKB's lock state, which the light follows.
- **Undoing.** The original definition is kept in the engine's undo record and written back, while the key still has Snappy's, when the setting goes off, at quit, when stopping for a restart, and after a crash at the next start.
- **Losing it.** A keymap loaded over Snappy's change, as `setxkbmap` or a layout switch does, is noticed through XKB's own notices and reported as Caps Lock lost.
- **Refusing.** Snappy refuses when the session's XKB options remap Caps Lock (`caps:escape`, `ctrl:nocaps`, and the like), or the key is no longer a plain Caps Lock, as after `xmodmap`.

## Workspaces

`src/windows/desktops.rs`. Window managers such as Xfwm4 keep part of every window on screen, so moving windows off screen can't hide them. Instead, Snappy adds a desktop named "Snappy" after the user's own, and moves parked windows there, frames untouched.

Its number is kept in a root window property, so a daemon restarted after a crash finds it again. The desktop guard compares the current desktop with the one workspaces started on.

## Limitations

- Only Xfwm4 is tested. Other window managers may differ in decorations, multi-monitor moves, and the tray.
- Grabs match modifiers exactly, so desktop shortcuts that use fewer of the Snappy key's modifiers don't collide with Snappy's, and GNOME, KDE Plasma, and Xfce bind nothing to Ctrl+Alt+Super. A Snappy key of fewer modifiers can reach theirs: Xfwm4 switches workspaces with Ctrl+Alt and the arrows, so a Snappy key of Ctrl+Alt is refused wherever Xfwm4 holds them.
