# X11

This page is for anyone working on Snappy's X11 adapter, `crates/x11`. It explains how Snappy finds and moves windows under X11, watches drags, registers shortcuts, draws zones, and handles Caps Lock and workspaces. What it shares with the other Linux adapters is in [Linux](linux.md).

The adapter talks to the X server with `x11rb`, which is pure Rust and needs no C libraries. It works with window managers that follow the EWMH standard, which most do, and it's tested with Xfwm4, with and without its compositor.

## Threads

X11 has no rule about which thread runs the event loop. So Snappy opens two connections to the X server (`src/app.rs`): the event loop reads events on one, and the engine thread makes its window requests on the other.

Shortcut grabs and input requests go out on the event connection, so their events arrive where they're read. The overlay has a thread of its own, which also runs the tray.

## How Snappy finds and moves windows

Under X11, the window manager keeps a list of the windows it manages, and moves windows when asked through standard messages. Snappy works through those, never around the window manager. The code is in `src/windows/`.

- **Which windows.** Managed windows come from the window manager's stacking list, `_NET_CLIENT_LIST_STACKING`, top first. The window under the pointer is the topmost visible one that contains it.
- **Frames** include the window manager's decorations (`_NET_FRAME_EXTENTS`), and leave out shadows that apps draw themselves (`_GTK_FRAME_EXTENTS`).
- **Moves** are requests to the window manager (`_NET_MOVERESIZE_WINDOW`). A maximized window is unmaximized first.
- **Focusing** asks the window manager to activate the window (`_NET_ACTIVE_WINDOW`), as a pager would.
- **App identifiers** come from each window's `WM_CLASS`.
- **Which windows Snappy manages.** A window qualifies when it's a normal top-level window, isn't a dialog belonging to another window, isn't full screen, and allows moving and resizing.

## How Snappy notices changes

Snappy hears about moves only for the windows it tracks (`src/events.rs`). Listening on the root window instead would wake Snappy for every frame of every window that moves.

Properties on the root window report windows opening and closing, focus changing, and the desktop changing. Display changes come from RandR, the work area (`_NET_WORKAREA`), and the screen's DPI setting (`Xft.dpi`). Each monitor's work area is worked out from the space panels reserve.

## How Snappy watches a drag

Snappy watches the mouse with XInput 2's raw events on the root window (`src/input.rs`). These keep arriving even while the window manager has grabbed the pointer to move a window, and they don't grab anything themselves.

Raw key events are watched only during a drag. Snappy follows the modifier keys from those events, in order, starting from what was held when the drag began. So a release reports the modifiers held when the button came up. Asking the X server afterwards could already see a modifier that was let go right after the button.

## Shortcuts

Shortcuts are key grabs on the root window, made once for each combination of Caps Lock and Num Lock, so they work whatever the lock keys are doing (`src/hotkeys.rs`). If a grab is refused, another program holds the chord, which is also how Snappy checks whether a chord is free.

On the usual evdev keymaps, Snappy's physical key codes map straight to X keycodes (`src/keymap.rs`), so shortcuts stay on the same keys whatever the layout. Key repeat is set up so that holding a shortcut fires it once.

A grabbed key's release goes to the grab too, so a shortcut whose release matters hears its key come up, even after Caps Lock, standing for the Snappy key, was let go first.

## Drawing the zones

Each display gets two windows that the window manager doesn't manage, one for zones and one for window outlines (`src/overlay/`). They're transparent where nothing's drawn, and take no clicks.

- **Without a compositor**, transparency doesn't work, so each window is cut down to the shapes it draws: the zone borders and the boxes behind numbers and captions.
- **Zones are blue.** X11 has no system accent color to read.
- **Outlines stay on top.** Window managers raise the window they focus, so the outlines window is raised again whenever the active window changes.

## Caps Lock as the Snappy key

Snappy changes what the Caps Lock key does for the current session, in XKB (`src/caps_lock/`). Afterwards, Caps Lock types nothing, sets the Snappy key's modifiers while held, and doesn't repeat. Snappy's own shortcuts and every other program simply see the modifiers, and Caps Lock never locks.

- **Presses.** Snappy grabs the key to hear when it's pressed. Only while it's down does it watch other raw key and button presses, to notice that something else was used.
- **A tap** toggles Caps Lock through XKB, and the light follows.
- **Undoing.** Snappy keeps the key's original definition in the engine's undo record. It writes it back when the setting is turned off, when Snappy quits or stops for a restart, and at the next start after a crash, as long as the key still has Snappy's definition.
- **Losing it.** Loading a new keymap over Snappy's change, as `setxkbmap` or switching layouts does, is noticed and reported as Caps Lock lost.
- **Refusing.** Snappy refuses when the session's XKB options already remap Caps Lock, such as `caps:escape` or `ctrl:nocaps`, or when the key is no longer a plain Caps Lock, as after `xmodmap`.

## Workspaces

Window managers such as Xfwm4 keep part of every window on screen, so moving windows off screen can't hide them. Instead, Snappy adds a desktop named "Snappy" after the user's own, and moves hidden windows there, frames untouched (`src/windows/desktops.rs`).

Its number is kept in a property on the root window, so a daemon restarted after a crash finds it again. Workspaces pause when the user switches to another desktop.

Sending a window to the back lowers it below the others, leaving it where it is. Xfwm4 doesn't offer EWMH's restack message, so Snappy asks with the request a client makes to restack itself, which window managers that follow ICCCM, Xfwm4 among them, carry out. A window held back goes back under the window that was just in front of it, if one in front overlapped it, with the same request naming that window, sent to the root window as an event: the X server refuses it from the client directly, since a managed window's siblings are frames, so ICCCM has clients restack relative to another window that way.

## Limitations

- **Only Xfwm4 is tested.** Other window managers may differ in decorations, moves across monitors, and the tray.
- **Desktop shortcuts and the Snappy key.** Grabs match modifiers exactly, so a desktop shortcut that uses fewer modifiers than the Snappy key doesn't clash with Snappy's. GNOME, KDE Plasma, and Xfce bind nothing to Ctrl+Alt+Super, the default Snappy key. A Snappy key with fewer modifiers can clash: Xfwm4 switches workspaces with Ctrl+Alt and the arrows, so a Snappy key of Ctrl+Alt is refused wherever Xfwm4 holds them.
